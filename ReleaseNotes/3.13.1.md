`cratis run` was leaving `cratis-stage-*` containers running after the command itself had ended. Two separate defects, either one enough on its own.

## Trusting the wrong process

Whether the sandbox had stopped was decided by watching the *Docker client process* this command started, not the container. Those are two different processes, and the client can exit while the container it asked for keeps running - Docker's own sig-proxy forwarding and `--rm` teardown are not instantaneous. A command that returns the moment its own child process ends can return before either has actually finished.

`StageSession.IsRunning()` now asks Docker directly (`docker ps --filter name=^<name>$`), and the stop path polls that until it says no or the timeout elapses, rather than inferring the answer from a different process's exit code.

## Only Ctrl+C was ever heard

This explains a container left running with **no Ctrl+C involved at all**. The command only reacted to `Console.CancelKeyPress`, which is scoped to a Ctrl+C typed at an attached interactive terminal. It does not fire for a plain `kill` from a process manager or an IDE's stop button - and, empirically (verified with a minimal repro against this exact .NET/platform combination), not reliably for a signal delivered any other way either. A closed terminal, a supervised process being told to stop, or a script invocation all left the container behind, because nothing was listening for what actually happened.

`ConsoleInterrupt` is replaced with `ShutdownSignal`, built on `PosixSignalRegistration` for `SIGINT`, `SIGTERM`, and - wherever a terminal can hang up - `SIGHUP`. The same graceful-shutdown path (stop the container, wait for Docker to confirm, then exit) now fires regardless of which of those asked for it.

## Verification

Unit specifications cover what can be asserted deterministically: the container-state parsing, and the platform-dependent signal list. The rest was verified against a real running sandbox rather than only in-process:

- A real Ctrl+C sent through a pseudo-tty's line discipline (the actual byte a terminal sends, not a simulated cancellation) - container fully stopped and removed.
- The controlling terminal closing outright (a real `SIGHUP`) - same result, and this is the case the previous build had no path for at all.

Both left no container behind. The previous build left one running indefinitely in both cases, confirmed by reproducing them first against the code on `main`.

1519 specifications pass, and a Release build (where the analyzers this repository builds under actually run).
