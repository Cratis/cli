Two related things: `cratis run` no longer starts a moving image tag, and the Stage and Screenplay packages move to the releases that carry a document's interactions.

## The tag

`cratis run` started `cratis/stage:latest`. The CLI plans artifacts with a *specific* version of the Stage rendering packages, and the container is what reads them - so a known renderer was paired with whatever happened to be published most recently. The two then drift apart on somebody else's release rather than on an upgrade here, and the symptom arrives at a user who changed nothing and has no way to explain it.

The default is now the version of the Stage packages this CLI was built against, read from the assembly rather than written down, so it cannot fall out of step with the reference it describes. Every Stage release publishes an exact tag, so the version a renderer came from is always a tag that exists.

A prerelease or unreadable version falls back to `latest`, because a locally built CLI should still be able to start a sandbox. `--tag` is untouched and still overrides, which is how a newer or older sandbox gets tried on purpose.

## The packages

Stage 3.22.0 to 4.0.0 and Screenplay 4.16.0 to 4.17.0. Together those are what let a `.play` document's `on click / execute SomeCommand` survive translation into the scene the container serves; before them the renderer simply dropped it.

Stage now has its own version property in `Directory.Packages.props`, next to the one Screenplay already had. The packages and the image tag are the same number by construction, so they cannot be bumped independently by accident - which is the failure this change exists to prevent.

## Verification

1508 specifications and a Release build. The new ones assert the default names the release the renderer came from, that it is not a moving tag, that it parses as a version so it can be a tag that exists, and that a run with no `--tag` uses it.
