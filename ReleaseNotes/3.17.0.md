## Why

`cratis update` only ever touched the CLI itself - a Stage sandbox image could sit at a version months old with nothing telling the user one existed. The per-command "update available" hint had the same gap.

## What changed

- `StageImage` reads what `docker images` already reports for `cratis/stage` locally and picks the newest tag that parses as a version, skipping `latest` and locally-built git-describe tags. No image pulled means no tag to read - the signal everything downstream treats as "say nothing".
- `StageImageUpdate` hands that tag to `UpdateChecker.CheckForUpdate` with `Cratis.Stage.Contracts` as the package - the same caching, freshness window, and NuGet lookup every other package already gets checked against, reusing the existing logic rather than duplicating it. A Stage image and its Contracts NuGet package release together, the same relationship `ServerPackageId` already relies on for the Chronicle server.
- `Program.cs`'s per-command hint now also checks the Stage image, printing a line only when a local image exists and something newer is out.
- `cratis update` (`SelfUpdateCommand`) checks and pulls a newer Stage image too, but only when one is already present locally - most users never run `cratis run`, and a multi-hundred-megabyte pull nobody asked for is not what updating the CLI should mean.
- Extracted the small "run docker, read what it wrote" helper `StageSession` already had into `DockerCli`, so the new local-image check and the existing container lifecycle calls share one implementation.

## Verification

- `dotnet build -c Release`: clean.
- `dotnet test -c Release` (Cli.Specs): 1526/1526 passing (2 new spec files).
- Verified end to end against the real Docker images and real NuGet on this machine: with `cratis/stage:4.4.0` present locally (the newest published tag), the check correctly reports up to date; simulating an older local tag against the real `Cratis.Stage.Contracts` NuGet package correctly reports `4.4.0` as available.
